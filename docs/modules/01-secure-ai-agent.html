Secure an AI agent that can take actions

A chatbot produces text. An agent does things. Here the model is completely fooled by an injected instruction, and it still does not matter, because a tool gateway refuses the dangerous action.

Open the lab handout View the code

Maps to OWASP LLM01, LLM06, LLM07 About 2 to 3 hours Python 3.11+

1. Scenario

Northwind Retail (fictional) runs an internal IT support agent with three tools: read support documents, create a ticket, and look up assets. One document the agent reads contains a hidden instruction telling it to fetch a restricted record. You attack it, then harden it.

3. The controls

ControlWhat it prevents
Dedicated agent identityActions that cannot be attributed or governed
Allow-list per workflowTools the task never needed
Short-lived, single-use, tool-scoped credentialsStolen or reused access
Human approval, bound to one exact callSilent high-impact actions
Input trust labelsTreating retrieved text as instructions
Complete tool-call loggingBlind spots in investigation
Emergency revocationNo way to stop an active incident

Challenge 8 removes controls one at a time. Removing one is survivable. Removing the allow-list and the approval together lets the manipulated model reach the record. That is defence in depth, demonstrated.

4. Honest limits

  • The model is a deterministic mock, chosen so the proof rests on architecture.
  • The gateway issues and redeems its own credentials and approvals are decided in code. In production an identity provider issues tokens, tool backends validate them, and approvals arrive over a channel the agent cannot write to.
  • The two-agent escalation scenario in the project README is a planned extension and is not built yet.
All data is fictional. The insecure agent is insecure on purpose: do not deploy it.
